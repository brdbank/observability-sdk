Observability SDK Migration

Project Plan — Tugane Platform, Development Bank of Rwanda · July 2026

1Executive Summary

The Tugane platform operates 11 NestJS microservices that collectively handle guarantees, loans, procurement, payments, and monitoring for BRD Rwanda. Each service was built with its own observability stack—Winston loggers, Morgan middleware, custom LoggerService classes, Kafka-based log shipping, and hand-rolled HTTP exception filters. The result: no trace correlation across services, no distributed tracing, inconsistent log formats, no unified metrics, and no way to diagnose cross-service failures without manually reading logs on individual machines.

Current State

  • 11 microservices, each with duplicated logging infrastructure (Winston + Morgan + LoggerService + Kafka logging client)
  • No distributed tracing—requests crossing service boundaries lose all context
  • No standardized metrics—no RED dashboards, no SLO tracking, no alerting on error rates
  • Debugging production issues requires SSH into individual machines and grepping log files
  • Mean Time to Detect (MTTD) and Mean Time to Resolve (MTTR) are unmeasured and high

Future State

  • Every service instrumented with @brdrwanda/observability—structured JSON logs with trace_id, request_id, and span_id on every line
  • Distributed traces flow across all service boundaries via W3C traceparent propagation
  • Prometheus metrics (RED: Rate, Errors, Duration) exported automatically per service
  • Grafana dashboards with bidirectional signal correlation: metrics → traces → logs → metrics
  • Automated alerting on error rate spikes, high latency, service down, and log anomalies

2Project Background

Existing Observability Challenges

Every Tugane service was built independently with a copy-pasted logging pattern:

ComponentWhat it doesProblem
LoggerServiceExtends NestJS Logger, wraps Winston with contextDuplicated in every service (50+ files reference it). No trace correlation.
Winston + DailyRotateFileWrites JSON logs to rotating filesLogs stored on local disk. Lost on container restart. No centralized search.
Morgan middlewareHTTP access loggingSeparate format from Winston. Duplicates request/response logging.
Kafka log producerShips logs to logging.info/logging.warn topicsExtra latency on every request. Kafka dependency for logging creates cascading failures.
HttpExceptionFilterCatches exceptions, logs themCustom per-service. Inconsistent error classification.
createLoggingContextWithIdManual correlation IDsDeveloper must remember to call it. IDs don't propagate across services.

Why the SDK Was Built

The @brdrwanda/observability SDK was purpose-built to replace this entire stack with a single, zero-config package that provides:

  • Structured logging (Pino) with automatic trace context injection—every log line gets trace_id, span_id, request_id without developer effort
  • Distributed tracing via OpenTelemetry with W3C traceparent propagation
  • Prometheus metrics (HTTP RED metrics, Node.js runtime, custom business metrics)
  • Health checks (/health endpoint) for Kubernetes readiness/liveness probes
  • Auto-instrumentation of HTTP, Kafka, Redis, Sequelize, and scheduled jobs
  • Error classification (401→authentication_failed, 400→validation_failed, 500→server_error)

Why Migration Is Necessary

Simply installing the SDK alongside existing code creates conflicts—two logging systems writing to stdout, two exception filters competing, and the legacy LoggerService continuing to produce unstructured logs that bypass trace context. The legacy code must be systematically removed per-service to realize the SDK's full value.

5Objectives

Technical Objectives

  • Standardize observability infrastructure across all 11 microservices using a single SDK
  • Achieve end-to-end distributed tracing from API Gateway through every downstream service
  • Enable Prometheus metrics collection with consistent naming and labeling
  • Instrument all communication channels: HTTP, Kafka, Redis, Sequelize, scheduled jobs
  • Correlate all three signals (logs, traces, metrics) bidirectionally in Grafana

Business Objectives

  • Reduce MTTR: Enable root-cause analysis in minutes instead of hours by following a single trace_id across all services
  • Improve troubleshooting: Any engineer can diagnose a production issue using Grafana without SSH access to servers
  • Standard dashboards: Every service gets the same RED dashboard layout, reducing cognitive load when context-switching between services
  • Faster onboarding: New developers and new services get full observability with 5 lines of config

Operational Objectives

  • Eliminate duplicated code: Remove ~90 files of copy-pasted logging infrastructure across 11 services
  • Centralize instrumentation: SDK updates propagate to all services via npm update instead of copy-pasting changes
  • Remove Kafka logging dependency: Logs flow to Loki via Promtail/stdout, eliminating the fragile Kafka-based log shipping
  • Enable SLO tracking: Standardized metrics enable defining and tracking Service Level Objectives

6Migration Strategy

Three-Level Approach

We migrate one service at a time, not everything simultaneously. Each service progresses through three levels. A service at Level 1 is already delivering value; Level 3 is full completion.
LevelNameOutcomeEffort
L1 Platform Readiness SDK installed, exporters configured, core infrastructure connected. Service emits traces and metrics alongside legacy code. 0.5–1 day
L2 Observability Design Endpoints inventoried, critical flows identified, metrics/logs/traces/dashboards/alerts designed per endpoint. 1–2 days
L3 Legacy Migration & Validation Legacy code removed, SDK is sole observability provider, dashboards published, alerts configured, production validated. 2–5 days (varies by service complexity)

14Migration Playbook

This is the step-by-step checklist developers follow for each service. Detailed code examples are in Migration Guide and Migration Checklist.

14.1 Preparation

  • Completed Microservice Assessment (Section 8)
  • Completed Endpoint Inventory (Section 9)
  • Completed Endpoint Classification (Section 10)
  • Completed Observability Design (Section 11)
  • SDK version pinned in package.json
  • Local sandbox running (OTel Collector, Tempo, Loki, Prometheus, Grafana)
  • Feature branch created from main

14.2 Development

  • Install SDK: npm install @brdrwanda/observability
  • Configure main.ts: setupProcessErrorHandlers(), NestPinoLogger
  • Configure app.module.ts: ObservabilityModule.forRoot() with service-specific config
  • Add instrumentations: HTTP, Kafka, Redis, Sequelize as needed
  • Replace every LoggerService injection with ObservabilityLogger
  • Remove createLoggingContextWithId() calls (SDK injects context automatically)
  • Remove custom HttpExceptionFilter (SDK provides one via APP_FILTER)
  • Remove Morgan middleware from app.module.ts
  • Remove Winston configuration and transports
  • Remove Kafka logging producer (logging.info / logging.warn topics)
  • Add @Span() decorators on critical methods per observability design
  • Add custom business metrics per observability design
  • Add trace propagation headers on inter-service HTTP calls
  • Replace console.log with this.logger.info()
  • Delete unused files: logger.service.ts, morgan.middleware.ts, winston.config.ts
  • Uninstall packages: npm uninstall winston nest-winston winston-daily-rotate-file morgan

14.3 Testing

  • All existing tests pass
  • Service starts without errors
  • Structured JSON logs appear on stdout with trace_id
  • No Winston/Morgan output in logs
  • /health returns 200
  • /metrics returns Prometheus format
  • Traces appear in Grafana Tempo
  • Logs appear in Grafana Loki
  • Metrics appear in Prometheus
  • Cross-service trace propagation works (same trace_id in upstream and downstream)

14.4 Deployment

  • PR reviewed and approved
  • Deploy to staging environment
  • Staging validation passes (repeat Testing checklist)
  • Rollback plan documented and tested
  • Deploy to production during low-traffic window

14.5 Rollback Plan

  • Previous deployment artifact retained
  • Rollback trigger: error rate >10% or service-down alert within 30 min of deploy
  • Rollback action: redeploy previous version via CI/CD
  • Rollback verification: error rate returns to baseline, service healthy
  • Post-rollback: root cause analysis, fix, re-attempt migration

14.6 Validation & Closeout

  • Production dashboards populate with real data
  • Alerts configured and tested
  • 5-day hypercare period completed without rollback
  • Definition of Done checklist completed (Section 20)
  • Lessons learned documented (Section 22)
  • Service marked complete in Project Tracker (Section 16)

20Definition of Done

A service migration is complete when ALL items are checked. This checklist is signed off by the Tech Lead before marking a service as "Production" in the Project Tracker.
  • Endpoint inventory approved — every REST endpoint, Kafka consumer/producer, and scheduled job documented
  • Critical endpoints classified — scoring model applied, classification reviewed by PM
  • Observability designed — logs, metrics, traces, dashboards, alerts defined for all Critical/High endpoints
  • SDK configured — ObservabilityModule.forRoot() with correct serviceName, exporter, instrumentations
  • Logs standardized — all logging through SDK's Pino logger; trace_id present on every log line
  • Traces verified — end-to-end distributed traces visible in Grafana Tempo with correct span hierarchy
  • Metrics exported — /metrics endpoint returns Prometheus format; Prometheus scraping successfully
  • Business metrics implemented — all metrics from observability design registering data
  • Dashboard published — Service Overview (RED), Runtime, Logs & Traces dashboards provisioned in Grafana
  • Alerts configured — platform alerts + service-specific alerts active; notification channel verified
  • Legacy removed — zero references to Winston, Morgan, LoggerService, createLoggingContextWithId, custom HttpExceptionFilter
  • Legacy packages uninstalled — winston, nest-winston, winston-daily-rotate-file, morgan removed from package.json
  • Tests pass — all existing tests pass; no test modifications required beyond logger mocking
  • Production deployed — service running in production with SDK
  • Hypercare passed — 5 business days stable, no rollback, alerts tuned to production traffic
  • Documentation updated — service-specific notes added to migration docs if any deviations from standard playbook
